# Org Canvas Chat

The agent chat that lives in the right panel of the org canvas (the **Chat** tab of `OrgRightPanel`, rendered by `SidebarChat`). This doc covers the chat subsystem: the Zustand store, autosave + live-sync persistence, the send/stream path, the planner fan-out → sub-agent cards, the attention-list intro, and title generation.

**Sibling doc:** `CANVAS.md` — the canvas itself (projection pipeline, categories/geometry, `+` menu, drag/drop, edges/connections, deep links, right-panel layout). Read it for anything that isn't the chat. The two are intentionally intertwined (the store exists *for* bidirectional chat ↔ canvas flow), so cross-references are expected.

The agent-proposal flow (`<ProposalCard>` rendered inline in chat, Approve/Reject via `approval`/`rejection` fields on user messages) is documented in `CANVAS.md` under "Agent-proposal flow" — it creates canvas entities, so it lives with the canvas doc. The chat-side consequence of approving a *feature* proposal (the planner fan-out → `<SubAgentRunCard>`) is documented here.

## The short version

- `src/app/org/[githubLogin]/_state/` — Zustand store + side-effect hooks for the canvas chat. `canvasChatStore.ts` is the source of truth for conversations, messages, streaming state, and reserved slots (`proposals`, `subAgentRuns`, `artifacts`) that future canvas-bound features will fill. `useSendCanvasChatMessage.ts` owns the streaming send path (fetch → `useStreamProcessor` → store writes). `useCanvasChatAutoSave.ts` is the write-through subscription that persists messages to `chat_conversations` via the org endpoint, AND the live-sync that merges server-appended rows back in. **Persistence is identity-based, NOT count-based** — `persistedIdsRef` tracks which message *ids* are on the server; the save delta is "local ids not yet persisted" and live-sync MERGES server rows by id (never wholesale-replaces). The pure invariant helpers live in `canvasChatPersistence.ts` (`seedPersistedIds` / `computeUnsaved` / `mergeServerMessages`) so the "never lose a message" contract is unit-testable without the store. This replaced an older count + seed-offset scheme that could shift the save window by one and silently drop the user's first message when a Pusher nudge interleaved with a PUT. The store is **org-canvas-scoped on purpose** — the dashboard chat keeps its own local state and does NOT use this store.
- **Org chat → agent toolset wiring (capability registry).** `src/app/api/ask/quick/route.ts` is the single chat stream endpoint; when `orgId` is supplied (the canvas chat, not the dashboard chat) it calls `runCanvasAgent`/`ln` after a `validateUserBelongsToOrg` check. The org tools + prompt suffix + readonly strip set are no longer merged ad-hoc — they're composed from `CAPABILITY_REGISTRY` in `src/lib/ai/capabilities.ts`. Each **capability** bundles a `buildTools` factory, a prompt snippet, and its write-tool names. Every resolved capability's tools are registered, but only `roadmap`, `planner`, `graph_walker` and `concepts` emit their snippets in the system prompt; `whiteboard`, `research`, `connections`, `html_pages`, `infra`, `strut`, `stakwork_workflows` and `prompts` add no prompt text — their instructions live in the graph's "Jamie Capabilities" concept tree. Prompt snippets live in `src/lib/constants/prompt.ts` (`getRoadmapCapabilitySnippet`, `getWhiteboardCapabilitySnippet`, `getPlannerCapabilitySnippet`, `getResearchCapabilitySnippet`, `getConnectionsCapabilitySnippet`; `getCanvasPromptSuffix` is the back-compat full inline composition). Adding a capability = new entry in `CAPABILITY_REGISTRY` (factory + snippet; add it to `PROMPT_SNIPPET_CAPABILITIES` only if its snippet must ride in the prompt); `composeCapabilityTools` / `composeCapabilityPromptSuffix` / `composeWriteToolNames` pick it up automatically.

## Gotchas

- **Canvas chat state lives in `useCanvasChatStore` (`_state/canvasChatStore.ts`), not in `SidebarChat` local state.** The store exists because several upcoming features — LLM-generated `propose-canvas-change` artifacts (rendered as both a chat card AND a halo on the affected canvas node), sub-agents (kicked off from chat, surfaced on the nodes they're working on), live task-status / PR-list artifacts — create bidirectional flow between the chat and the canvas itself. Two `useState` islands talking via prop drilling would be miserable. The store is the single source of truth; chat and canvas both subscribe with narrow selectors. **Conversation lifecycle is owned by `OrgCanvasView`, not `SidebarChat`** — `OrgCanvasView` calls `startConversation` once `chatReady` is true (workspaces + hidden list + share preload all resolved), then keeps the conversation's `context` (canvas ref, breadcrumb, selected node id) in sync via `updateActiveContext`. `SidebarChat` is a pure renderer over the active conversation; it never owns chat state, so unmounting it (e.g. a tab switch) is cheap and idempotent. **Auto-save runs at the page level**, not inside `SidebarChat` — `useCanvasChatAutoSave` mounts in `OrgCanvasView` and survives chat unmounts, so pending writes never get dropped by tab navigation.
- **Store performance contract — read this before adding a consumer.** The streaming write path commits one `set()` per stream chunk (~50/sec). To keep that cheap:
  1. **Always select.** Never call `useCanvasChatStore()` without a selector — that subscribes to the whole store and re-renders on every text-delta. Use `useCanvasChatStore((s) => s.x)` instead. The single biggest footgun.
  2. **Use `useShallow` for derived collections.** A selector that returns a fresh array/object on every call (e.g. `Array.from(s.conversations.values())` or `messages.map(...)`) defeats Zustand's `Object.is` bail-out → re-renders constantly. Wrap with `useShallow` from `zustand/react/shallow`.
  3. **Stable empty-array sentinels.** When a selector might return `undefined` (e.g. no active conversation), fall back to a module-level `const EMPTY_X: T[] = []` instead of `?? []` — the latter creates a new `[]` every time, breaking identity equality. See `EMPTY_MESSAGES` / `EMPTY_TOOL_CALLS` in `SidebarChat.tsx`.
  4. **Select narrowly.** `SidebarChat` selects `messages`, `isLoading`, `activeToolCalls` separately rather than the whole conversation object, so the canvas's `proposals` selector is unaffected by chat streaming, and vice versa. When the canvas grows badge/halo subscribers for proposals/sub-agents/artifacts, follow the same pattern: select the specific slice you render, not "the conversation."
- **Identity-based autosave — never lose a message.** `useCanvasChatAutoSave` tracks a per-conversation `persistedIdsRef: Set<messageId>`, not a count. The save delta is `computeUnsaved` (local messages whose id isn't persisted, in order — so a creating POST always *leads with the real first user message*, never a placeholder-titled assistant row), and live-sync uses `mergeServerMessages` (keep all local rows, append server rows we don't already have, by id). Both operate on identity, so a mid-turn Pusher nudge can never drop a local message: merge only adds; the delta only sends ids not yet on the server. The merge runs only when the conversation is idle (no unsaved local messages, not streaming, no save in flight); a nudge that arrives mid-turn is deferred and retried after the next successful save. Ephemeral seeds (the AttentionList intro; the messages a joined/share conversation already has on the server) are pre-seeded into `persistedIdsRef` so they're never re-sent. The pure helpers in `canvasChatPersistence.ts` are unit-tested in `src/__tests__/unit/canvas/canvasChatPersistence.test.ts` (incl. the seed→user→planner-nudge lifecycle that used to drop the first message).
- **Conversation title self-heals.** The title is generated once at create time from the first user message (`generateTitle` in `src/lib/ai/conversationHelpers.ts`). If the creating POST's delta ever leads with a non-user row, the title freezes as `UNTITLED_CONVERSATION`; the org PUT route recomputes it from the full message list the moment a user message lands (and the history popover treats the placeholder as empty, falling back to the first-user-message preview). The identity-based autosave (above) makes the freeze rare — the creating delta now always leads with the real user message — but the heal covers legacy rows.
- **Adding a canvas-bound chat feature?** Use the reserved slots in `useCanvasChatStore`. Proposals → `state.proposals` map; long-running agent runs → `state.subAgentRuns`. Each is keyed by id. What a message hands the reader to look at is not a slot: it rides on the message as `message.artifacts` (see below), and the older `state.artifacts` / `message.artifactIds` registry is unused. If you find yourself emitting a Pusher event from the chat to the canvas (or vice versa), stop — that's what the store is for.
- **Synthetic intro / "top items needing your attention".** First registered artifact type is `attention-list` (`src/app/org/[githubLogin]/_components/AttentionList.tsx`). On fresh canvas entry `OrgCanvasView` fetches `/api/orgs/[githubLogin]/attention?limit=3` (backed by `src/services/attention/topItems.ts`, which fans 4 signal queries — halted/failed workflows, features awaiting user feedback, tasks with FORM artifact, ready-to-review COMPLETED — across the user's accessible workspaces in the org), then seeds `startConversation` with one synthetic assistant message + a registered artifact of `type: "attention-list"`. The seed is **ephemeral**: `startConversation` accepts `ephemeralSeedCount`, which `useCanvasChatAutoSave` reads to skip leading messages from the first POST/PUT — so the synthetic intro never lands in `chat_conversations` and never leaks into `?chat=<shareId>` shares. Skip conditions: `?chat=<shareId>` is present (forking), or `sessionStorage["hive:attention-dismissed:<login>"] === "1"` (user clicked × this session). Dismissal flows through `state.dismissedArtifactIds` (a generic per-session dismiss set) — `OrgCanvasView` subscribes once and writes the sessionStorage flag whenever an `attention-*` id lands in it. Per-card behavior (callbacks, etc.) goes through store actions, not function-valued artifact data, so the artifact registry stays serializable. (`MessageArtifacts` in `SidebarChat` does not read this registry: it renders the refs a message carries — next bullet.)
- **A message carries artifact refs; content is read through one loader; `kind` is how Hive shows one.** What Jamie hands the reader to look at — a plan, a screenshot, a pod's browser, a pull request, logs — rides on the message as an `ArtifactRef` in `message.artifacts` (`_state/canvasChatArtifacts.ts`): `id`, `kind`, `title`, an optional `label` and `summary`, and a `source` that points at where the content lives. Nothing is registered in `state.artifacts`. The content — what a viewer draws (`ArtifactContents`) — is never stored on the message: `useArtifactContent` (`_components/artifacts/useArtifactContent.ts`) reads it when the artifact has been on screen in the chat or the panel opens, through React Query, so the chat and the panel showing the same artifact share one read. A `pull_request` ref is the one inline kind read live: its content is the state the job reported, and `useArtifactContent` overlays GitHub's current state — from `GET /api/orgs/[githubLogin]/strut/pull-request?repo=&number=`, read with the viewer's own GitHub token, so GitHub decides what they see and nothing has to tie the PR to a job — every 30 s while it is on screen, until the PR is merged or closed; a PR reported merged or closed is never read. `kind` names the renderer, never the job: a plan is `markdown`, a screenshot is `image`, a pod or a web page is `url`. What it is to the reader goes in the free-text `label`, which is displayed and never switched on. The kinds: `markdown`, `html`, `image`, `video`, `audio`, `pdf`, `url`, `diff`, `pull_request`, `code`, `log`, `json`, `graph` (a workspace's graph on the graph workbench, a proposal's change drawn on it) and `run_graph` (what a strut run did in a workspace's graph, call by call — the run graph of `components/strut-run-graph`, read live through `/api/workspaces/<slug>/strut/runs/<id>/graph`). **`_components/artifacts/registry.ts` is the one place a kind is switched on** — each entry gives where the kind sits in the chat and what draws it there (`chat`: a `row` with its `Meta` state — PR, claims, pod, page; a `media` `Thumb` in the message's strip — screenshot, video, walkthrough, a graph or graph trace drawn small; a `preview`'s first `Lines` of a document; or nothing, folding it into the message's "N more" line — logs, JSON, code, diffs), its `Panel` view (on the artifact panel, `ArtifactPanel`), and what can be done with its content (`copyText`, `address`). `ChatArtifacts` lays a message's artifacts out that way; each piece reads its content once it has been on screen, and only if it draws some. Adding a kind = an entry in `ArtifactContents` with its parser + a registry entry. Two refs are the same artifact when they resolve to the same thing (`artifactIdentity`): a job's file by its swarm and key, a pull request by repo and number, a stored page by its slug, an address by its URL — whatever the agent named it that turn; only inline content frozen on the message goes by `id`. The chat shows an artifact once, under the message that reported it last (`indexArtifactCards`), so a plan re-reported every turn appears once, where it was last revised. Only inline snapshots have versions ("v2"); the panel steps between those, following the newest unless the reader stepped back.
- **Refs and content are parsed before they render; addresses are checked before they are framed or linked.** A ref comes out of stored JSON and content out of another system, so `parseArtifactRefs` (at every hydration: `toCanvasMessages`, `hydrateServerMessages`, the fork, the `?chat=` preload) and `parseArtifactContent` (inside the loader hook) keep what is whole and drop the rest — nothing is repaired. An artifact's address was written by an agent: it becomes a link only through `artifactHref` (the registry's entries hand over the address as written) and reaches the mini browser's frame only through `webAddress` — http(s) only, both. A PDF is framed only when `framablePdfAddress` passes it (Hive's own origin, or bytes the page holds), because the browser's PDF viewer cannot run in a sandboxed frame. The mini browser's sandbox confines pages from elsewhere; a page on Hive's own origin is Hive itself and is no more confined in the frame than in a tab of its own. Stored HTML goes through `HtmlArtifactFrame` like everywhere else.
- **The writer and the reader: strut jobs.** `ArtifactSource` has two shapes: `inline` (the content is on the ref — an address, or something small) and `graph` (`swarmId` + `key`: something on that swarm's strut, `key` being strut's own link to it — `/jobs/<job>/files/<path>` for a file in a job's directory, `/artifacts/<runId>/<path>` for a run's own). An `inline` ref is read straight off the ref. A `graph` ref goes through the loader (`ArtifactLoaderContext`'s default, `readStrutArtifact` in `useArtifactContent.ts`), which reads it through **one Hive route**, `GET /api/orgs/[githubLogin]/strut/artifacts?swarmId=&key=` — session auth, the swarm must be a workspace of the org the caller can read, the key must be one of the two link shapes AND name a job or run a `StrutRun` row says Hive launched there, then the bytes are streamed from the swarm with strut's `content-security-policy: sandbox` and `x-content-type-options: nosniff` kept and `cache-control: private, no-store`. Text kinds (`markdown`, `log`, `code`, `json`) are fetched and shaped by the loader; media, a PDF and a `url` are handed to their viewers as that reader URL (Hive's own origin, so the PDF frame rule passes); a page strut wrote stays `html`, its content `{ swarmId, key }` (the second shape of `ArtifactContents.html`, beside tom's stored page by slug), and `HtmlArtifactFrame` reads the bytes through the same reader and renders them from a blob in its sandboxed frame — scripts on under its CSP meta tag, never a navigation to the reader, which serves the page static (strut's `sandbox` kept) for anyone who opens its URL. **The writer** is the `job_turn` completion handler (`services/strut-runs/job-turn.ts`, strut `plans/jobs.md`): `start_job` / `continue_job` (`lib/ai/strutTools.ts`) launch the org strut's seeded `job` workflow with a job id Hive minted, and when a turn settles the handler reads strut's resolved artifact list (`GET …/runs/<id>/artifacts`), maps it to refs (`mapStrutArtifacts`: a strut-relative url → `graph`; an absolute url or inline content → `inline`) and appends ONE assistant row (`source: { kind: "job", jobId, … }`, header `**Job · <jobId> · <title>**`, `artifacts` on the row — `StoredMessage.artifacts`) with the fan-out discipline of `canvas-strut-fanout.ts`. A successful turn that touched the knowledge graph also carries Hive's own card, after the job's refs: a `run_graph` ref (`{ workspace, run, calls, nodes }` inline, `run` the turn's `StrutRun` id) with one id per job (`run-graph-<jobId>`), so the chat shows one trace card per job, on its latest turn, and the panel steps back through the turns as its versions. The handler counts it from the run's log (`countStrutRunGraph`) beside the artifact list, bounded and best effort — no trace is ever a reason to retry — and indexes for events and names to the wake only the job's own refs. `ArtifactLoaderContext` lets a test or a demo stand in for the reader. Still open on the live path: live-sync only appends rows it has not seen (`mergeServerMessages`) and skips the rows of a turn this tab sent, so the job row reaches an open tab through the `job` Pusher nudge (a new row, not one patched in place — which is why the handler appends rather than patches). An `html` ref for a STORED page would sit beside `HtmlPageCard` (built from `save_html` tool output) as a second card for the same page — the job writer emits `html` only for a page on the swarm, which has no stored twin, so nothing collides.
- **A `graph` artifact is the workbench, or a brainstorm tree.** Content: `{ workspace, focus?, changes?, proposal?, layout?: "tree", label? }` (strut may send it as a JSON string; `mapStrutArtifacts` parses it). A tree is chosen by `isTreeArtifact` alone — `layout: "tree"`, an artifact id containing `brainstorm` (case-insensitive, e.g. `job-x:brainstorm-tree`) or a `label` of `Choice`/`Option`/`Question`; a stray `proposal`/`changes` is ignored, and a tree card with no `focus` shows "This brainstorm card has no root to open." and never the workbench. The panel is `ChoiceTree` (`artifacts/viewers/ChoiceTree.tsx`) instead of the workbench: IBIS-style `Question` nodes (key `question_id`) and `Option` nodes (key `option_id`; old trees use `Choice`, key `choice_id`, which render as options) — all labels unless `label` restricts — joined by `PARENT_OF` (Question→Question sub-question, Question→Option, Option→Question follow-up) — read by Cypher through `GET /api/workspaces/<workspace>/graph/choice-tree?focus=<focus>[&label=<label>[,<label>]]` (each node carries a `type`, `Question`, `Option` or `Choice`; legacy `Choice` nodes with `kind: "question"` render as questions) (the `/graph/nodes` REST listing can't: it drops unknown labels and misreports `node_type`), drawn left to right from `focus` along `PARENT_OF` descendants, each node 260px wide showing its `text` (else `name`, else ref_id) wrapped and clamped to 3 lines, with the full text and `quote` in a native tooltip; children are ordered by `option_id`, `choice_id` or `question_id` (numeric when both numeric) and labels join along the path — a sub-question (a question under a question) gets a number among its question siblings, an option a letter among its option siblings, appended to the nearest labelled ancestor's label (`1`, `1A`, `1B`, `2`, `2A`; root options `A`, `B`; the root and follow-up questions under an option have no own part and pass the label through, so `AA`, `AB`, and a sub-question under a follow-up under A is `A1`, its options `A1A`). Assumption, to match strut's `choice/tree`: two adjacent numbers are joined with a dot (`1.1`, options `1.1A`). Letters past Z fall back to the sibling number — polled every 15 s and on window focus. Options may carry read-only **effects** (`(Option)-[:HAS_EFFECT]->(Effect)`: `name`, `description`, `direction` pro/con, `impact` 0–1; `effects` on the `choice-tree` node): unselected shows a `data-effects-summary` (+N / −N), selected a `data-effects` Pros/Cons list of `data-effect` rows (name, impact %, bar, description); nothing renders, and heights don't change, when there are none. Unselected nodes are quiet: letter chip, text, a state dot/border style (chosen green, rejected muted + line-through, simulated dashed sky) and a tiny User/Bot icon (`title` "made by user/model"), no buttons. Clicking a node selects it (local state; click again or the pane to deselect): it shows full text, quote, state (non-open only) and made_by as text, and its actions — **Expand** (**Revisit** when rejected) and, for options (or no `kind`) only, **Go with**. A question is a plain heading with a help icon and left accent (no state colour; a sub-question shows its number in an outlined chip, the root and follow-ups none), always shows a "decided" tag when decided, shows `criteria` / `reversibility` when selected, and its only action is **Expand** (title "More options"); `speaker`, when set, replaces `made_by` as text and in the icon title. Node heights are estimated from text length and fed to the dagre `layoutTree`, re-run on selection change (`fitView` only on first load). The buttons only draft into the chat input: Expand / Revisit call `setPendingInputDraft` (replacing the input) with `Expand AB: "<text>" (<ref_id>)` (`Expand 2: …` for a sub-question; `Expand "<text>" (<ref_id>)` for the root or a follow-up), and Go with calls `appendPendingInputDraft` with `Go with AB: "<text>" (<ref_id>)`, appending a line so several options can be sent in one message; a selected node's height estimate (`estimateNodeHeight`) counts its criteria / reversibility rows and gaps, and the node is `min-h-full` so the border never clips; the user presses send. In the chat it is a small graph in the message's strip, and opens as the tree on the panel. On settle, `handleJobTurnSettled` also collects the `brainstorm-tree` graph artifact of the turn's last local `brainstorm` child run (`readBrainstormArtifacts`, from the turn's events) into the cards; the run's card REPLACES any ref the agent reported under `brainstorm-tree` (any kind, same position), and the delivery log carries `brainstorm: {found, launches, replaced, reason}`. `mapStrutArtifacts` also maps an agent's copy of the card (id `brainstorm-tree`, or inline content with string `focus` + `layout: "tree"`, any kind) to `graph`, and already-stored `json` tree cards open as the tree (`treeContentOfJson`, used by `JsonPanel`).
- **A job row is the record; Jamie's wake is the reply.** A job turn's row (`source.kind: "job"`) is what the job's agent wrote, in full — a code change lists files, functions and line numbers — so `SidebarChat` renders it as `JobTurnCard`, collapsed to its title and how the turn ended (Done / Needs an answer / Failed / Stopped / Lost); a click opens the full reply, and what stays visible collapsed is the job's **Question for you** or a failed turn's one-line reason. The artifact cards render under the card as for any message. The readable reply is the canvas agent's own turn: once the row lands (exactly once, on `appended`), `handleJobTurnSettled` schedules `invokeCanvasAgentOnJobTurn` (`services/canvas-strut-autoturn.ts`, the same runner as the settled-chat wake) in `after()`, with the outcome, the question and the titles of the cards; its wake message — and the strut capability snippet — tell the agent to write ONE short paragraph in its own words, never restate the entry, never list files/functions/line numbers, never describe the cards, or to `continue_job` when the user's instructions already answer the question, or to stay silent. Same gates as every autonomous turn (the owner's `canvasAutonomousTurns` opt-in, the master kill switch) and the same loop breaker, which now counts `start_job` / `continue_job` as launches alongside `dispatch_strut`. The callback's host rides to the handler as `StrutRunHandlerContext.publicBaseUrl` (what a `continue_job` made on the wake turn builds its callback URL from); the reconcile path has no request and falls back to the deployment's own URL. Stored job rows still reach the model as text on the next human message, header line included. Before the row lands, the launch alone is the card: `getPendingJobTurnsFromMessages` (`JobTurnCard.tsx`) walks the conversation in order and pairs each `start_job` / `continue_job` call strut accepted (`status: started | continued`) with the job row that follows it — a job has one unsettled turn at a time, and the server persists the launching turn before a job turn can settle — and a launch with no row yet renders `PendingJobTurnCard` (the title, a spinning **Running** pill) under the message that made the call, beside the raw tool card the way the strut chat card sits beside `dispatch_strut`. A pure projection like that card, so it survives reload and reaches other tabs with the persisted `toolCalls`, and it cannot stick: Stop cancels the run on strut, which posts back a Stopped row; a run strut never reports is reconciled to a Lost row after `STRUT_RUN_RECONCILE_MIN_AGE_MS`. A refused launch (`busy`, `error`) or an interrupted call draws nothing.
- **A job tells the chat what it is doing, live (strut plans/live-artifacts.md).** Every job turn's launch also registers `jobCallback` = `/api/strut-jobs/events?id=<row>&token=<the row's token>` (`dispatchStrutRun`); strut keeps the latest per job and POSTs a small `job.update` there for a shot, each walkthrough frame, a hold taken or let go, each check's evidence, a Verify's end. The route checks the token against the row and the job against the row's, forwards the update over Pusher (`CANVAS_JOB_UPDATE` on the conversation channel — links, never bytes) and, on `verify / done`, publishes the claims card's next version (`publishVerifiedVersion`) — only for a Verify a person started from the card, which hive marks in Redis when it asks strut to detach; a pass the job's agent runs on its own turn posts no row (its turn's row brings the card), and a person's Verify posts one line saying what changed against the card the chat showed (`describeVerify`: `"<claim>" unknown → supported`, or no change). The client keeps them in memory (`_state/jobLiveStore.ts`, never the record): the working card shows what arrived since it appeared (`JobLiveStrip`) minus anything the conversation already shows under the same link — a live item and a delivered artifact are matched BY URL, never by id. It stays small however much the job does: ONE tile for the newest recording (its newest frame) or shot, and one line counting the rest (`liveTally`: recordings and how many stopped, shots, holds, verdicts) — earlier and stopped recordings are counted, never drawn, since the job retries one that stopped. The tile opens on the artifact panel through `openLiveArtifact`, which carries the ref on the panel state (`ArtifactPanelState.live`) because the chat does not hold it yet; once the turn delivers it under the same graph key, the chat's own takes over. A row whose 202 said `jobCallback: true` is marked `liveUpdates`; the claims card's Verify then runs DETACHED (`{ detach: true }`, the toolbar says Verifying… until the pass ends, verdicts listed as they land), otherwise it waits on the pass as before. A `walkthrough` artifact (`browser/walkthrough`'s `walkthrough.json`) is a `graph` ref the viewer reads through the reader route and scrubs; it reads the manifest again on each update for its link, so a recording in progress fills in.
- **The artifact panel has its own pane; `state.artifactPanel` says what is on it.** A card calls `openArtifactPanel(identity, version?)` with the artifact's `artifactIdentity`; `openArtifactIndex()` puts the index of every artifact in the chat there instead (`identity: null`). `OrgCanvasView` watches `useArtifactPanelOpen()`: on the chats view the panel is a resizable pane right of the chat; on the canvas and graph views it takes the left panel (the canvas unmounts) while the chat stays where it is. In the chat a message's artifacts are laid out by their kind's `chat` placement (`ChatArtifacts`); one that waits on the reader (`artifactAsks` — an open PR, a claim needing a look) tops the panel's index. Escape, the panel's ×, changing conversation (`startConversation` / `setActiveConversation` clear the slot — an artifact belongs to the chat it came from) or leaving the page all close it.
- **Brainstorm board context (`brainstormFocus`).** While the canvas's Brainstorm tab (the desk) is mounted, `<Desk>` publishes the brainstorm in focus (or holding the selected card) `{ workspaceSlug, rootRefId, rootText, jobId?, selectedRefId?, selectedLabel? }` through the store action `setBrainstormFocus` (a top-level `brainstormFocus` slice, cleared on unmount / tab change). `OrgCanvasView` selects it narrowly and includes it in `updateActiveContext` (`ConversationContext.brainstormFocus`, the same pattern as `graphFocus`); `useSendCanvasChatMessage` sends it to `/api/ask/quick` beside the other hints, never in the visible message; the route validates it with `parseBrainstormFocus` (`lib/canvas/graph-focus.ts`, zod; workspace must be one the request is scoped to; texts stripped of prompt-breaking characters); `runCanvasAgent` passes it in the scope (and logs `[runCanvasAgent] brainstorm board` with root and job); `getCanvasScopeHint` adds "## Current brainstorm board" — the user is PROBABLY talking about this brainstorm; tree changes go through `continue_job` with the root's `job` and the user's words unchanged; a job that is not theirs means a teammate's brainstorm, so ask before `start_job`. The desk composes messages only from the selected card's toolbar or right-click menu — `appendPendingInputDraft` (Go with) and `setPendingInputDraft` (Deselect, Drop, Reopen, Expand / Ask Jamie for options); tapping a card alone writes nothing — and the user presses Send. Cards a person writes by hand are not chat messages: they're saved straight to the graph (see `CANVAS.md`, Brainstorm tab); `OrgRightPanel` flips to its Chat tab whenever a draft is pending.
- **Chat input prefill via `pendingInputDraft`.** A canvas affordance can compose a chat message *for* the user without a DB write or agent tool call: write the text to `useCanvasChatStore.pendingInputDraft` and switch the panel to the Chat tab. `<SidebarChatInput>` watches the slot in an effect, applies the value to its local `input` state, focuses + caret-to-end, then immediately clears the slot via `setPendingInputDraft(null)` so a tab-switch back doesn't re-apply. The user can edit and send normally. A sibling slot, `pendingInputAppend` (action `appendPendingInputDraft(text)`), **appends** instead of replacing: `SidebarChat` adds the text on a new line after what the user typed (taps made while the input is unmounted accumulate, joined with `\n`), focuses, then clears the slot. The brainstorm tree's **Go with** uses it so several options can be collected into one message; Expand / Revisit still replace via `pendingInputDraft`. The canonical use today is the Connections link-mode `+ Create connection` button (`Make a connection document between A and B`). This is the canonical pattern for "canvas affordance composes a chat message" — proposals, agent suggestions, etc. should reuse `pendingInputDraft` rather than reaching imperatively into the textarea ref.
- **Stop: the composer's Send becomes Stop while a turn runs.** From send until the reply ends, the conversation's `activeTurn` is set and every send waits for it: `useSendCanvasChatMessage` refuses, `ProposalCard` disables Approve / Reject, and a research kickoff goes to `pendingInputDraft`. `stopCanvasChatTurn` POSTs `/api/ask/abort` with the turnId; the server writes a Redis key (`services/canvas-turn-abort.ts`) that the instance generating the turn polls, aborting `streamText` — a running repo_agent tells stakgraph to stop, and sub-agents the turn dispatched but hadn't started are fanned out as `cancelled`. Only once the server accepts does the tab abort its own request and end the turn locally: unfinished tool calls become `interrupted` and a `source.kind: "stopped"` row follows. The server persists the same shape under `${turnId}-a*` (this tab keeps its own copy; the authored-turn filter skips the server's). `toModelMessages` — one function for server history and the client-sent history — gives every tool call a result and replays the stopped row as a notice from the user. Closing the tab never stops a turn; sub-agents that started after the reply ended run to completion. **Edit and send again:** a turn this tab stopped (`stoppedTurnId`) offers Edit on its message, which puts it in the composer (`editingTurnId`); sending then passes `replacesTurnId`, and the stopped turn leaves the transcript — locally (`removeTurn`; local rows carry the server's `${turnId}-…` ids, so a turn is one prefix on both sides) and on the server (`removeStoppedTurn`, only for the caller's own stopped turn per Redis, and only while it is still the last turn). A stopped turn whose reply is still being saved drops that save once replaced (`appendTurnMessages`' `requireRowId`).
- **The org page's views share this store.** Chats is the default (`/org/<login>`): the chat list (`ControlPanelList`, state from `useControlPanel`: the user's Jamie chats, each with the jobs it started — from their job-turn `StrutRun`s — and the PRs those jobs reported — from the chat's PR cards), the chat as the main column, the artifact pane beside it. Canvas (`?view=canvas`, or any canvas-only param such as `?canvas=` / `?r=`) keeps the chat beside it as always; graph (`?view=graph`) keeps it tucked away until "Ask Jamie". `orgPageView` in `useOrgView.ts` decides which view. The chats view (`ChatsLayout`) has no canvas, so anything asking for one there — a canvas-only param written into the URL by an in-chat link, a canvas deeplink chip's `pendingDeeplink` — sends the page to the canvas view carrying the chat (`canvasViewHref`). `OrgCanvasView` owns the conversation lifecycle in every view (`startConversation` once workspaces + the optional `?chat=` preload resolve, `updateActiveContext` on changes, `useCanvasChatAutoSave` at page level). Every "open this stored chat" affordance — the history popover, the automations inbox, chat list rows — goes through `openOrgConversation` (`_state/openOrgConversation.ts`); `startNewOrgConversation` is the shared "fresh chat in its own slot + drop `?chat=`" path. Don't add a fourth copy.
- **What's NOT in this store.** Voice transcript / mic state lives in `src/stores/useVoiceStore.ts` (separate concern, separate lifetime — mic-session-scoped, available across surfaces). When voice transcription wants to drop a finalized transcript into the canvas chat, it calls `useCanvasChatStore.getState().appendUserMessage(...)`. **The dashboard chat does NOT use this store.** `DashboardChat` keeps its own local state on purpose; the two surfaces are diverging. Don't try to unify them — when a feature lives on both, share the lower-level pieces (`useStreamProcessor`, message types), not the state layer.
