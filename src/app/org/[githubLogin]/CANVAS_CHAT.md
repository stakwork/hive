# Org Canvas Chat

The agent chat that lives in the right panel of the org canvas (the **Chat** tab of `OrgRightPanel`, rendered by `SidebarChat`). This doc covers the chat subsystem: the Zustand store, autosave + live-sync persistence, the send/stream path, the planner fan-out → sub-agent cards, the attention-list intro, and title generation.

**Sibling doc:** `CANVAS.md` — the canvas itself (projection pipeline, categories/geometry, `+` menu, drag/drop, edges/connections, deep links, right-panel layout). Read it for anything that isn't the chat. The two are intentionally intertwined (the store exists *for* bidirectional chat ↔ canvas flow), so cross-references are expected.

The agent-proposal flow (`<ProposalCard>` rendered inline in chat, Approve/Reject via `approval`/`rejection` fields on user messages) is documented in `CANVAS.md` under "Agent-proposal flow" — it creates canvas entities, so it lives with the canvas doc. The chat-side consequence of approving a *feature* proposal (the planner fan-out → `<SubAgentRunCard>`) is documented here.

## The short version

- `src/app/org/[githubLogin]/_state/` — Zustand store + side-effect hooks for the canvas chat. `canvasChatStore.ts` is the source of truth for conversations, messages, streaming state, and reserved slots (`proposals`, `subAgentRuns`, `artifacts`) that future canvas-bound features will fill. `useSendCanvasChatMessage.ts` owns the streaming send path (fetch → `useStreamProcessor` → store writes). `useCanvasChatAutoSave.ts` is the write-through subscription that persists messages to `chat_conversations` via the org endpoint, AND the live-sync that merges server-appended rows back in. **Persistence is identity-based, NOT count-based** — `persistedIdsRef` tracks which message *ids* are on the server; the save delta is "local ids not yet persisted" and live-sync MERGES server rows by id (never wholesale-replaces). The pure invariant helpers live in `canvasChatPersistence.ts` (`seedPersistedIds` / `computeUnsaved` / `mergeServerMessages`) so the "never lose a message" contract is unit-testable without the store. This replaced an older count + seed-offset scheme that could shift the save window by one and silently drop the user's first message when a Pusher nudge interleaved with a PUT. The store is **org-canvas-scoped on purpose** — the dashboard chat keeps its own local state and does NOT use this store.
- **Org chat → agent toolset wiring (capability registry).** `src/app/api/ask/quick/route.ts` is the single chat stream endpoint; when `orgId` is supplied (the canvas chat, not the dashboard chat) it calls `runCanvasAgent`/`ln` after a `validateUserBelongsToOrg` check. The org tools + prompt suffix + readonly strip set are no longer merged ad-hoc — they're composed from `CAPABILITY_REGISTRY` in `src/lib/ai/capabilities.ts`. Each **capability** bundles a `buildTools` factory, a prompt snippet, its write-tool names, and a `core` flag. The five: `roadmap` + `planner` (CORE, always in the prompt — the hot path: propose a feature, then drive it with `send_to_feature_planner`), and `whiteboard` + `research` + `connections` (LOADABLE — **progressive disclosure**). Loadable snippets are NOT in the up-front prompt; the core suffix carries a one-line menu and the agent calls the `learn_capability` tool to pull a snippet on demand (the tools themselves are always registered since the AI SDK fixes the toolset at call start). This keeps the always-on prompt ~8k tokens instead of ~13k. Prompt snippets live in `src/lib/constants/prompt.ts` (`getRoadmapCapabilitySnippet`, `getWhiteboardCapabilitySnippet`, `getPlannerCapabilitySnippet`, `getResearchCapabilitySnippet`, `getConnectionsCapabilitySnippet`; `getCanvasPromptSuffix` is the back-compat full inline composition). Adding a capability = new entry in `CAPABILITY_REGISTRY` (factory + snippet + `core` flag + `menuBlurb` if loadable); `composeCapabilityTools` / `composeCapabilityPromptSuffix` / `composeWriteToolNames` pick it up automatically.

## Gotchas

- **Canvas chat state lives in `useCanvasChatStore` (`_state/canvasChatStore.ts`), not in `SidebarChat` local state.** The store exists because several upcoming features — LLM-generated `propose-canvas-change` artifacts (rendered as both a chat card AND a halo on the affected canvas node), sub-agents (kicked off from chat, surfaced on the nodes they're working on), live task-status / PR-list artifacts — create bidirectional flow between the chat and the canvas itself. Two `useState` islands talking via prop drilling would be miserable. The store is the single source of truth; chat and canvas both subscribe with narrow selectors. **Conversation lifecycle is owned by `OrgCanvasView`, not `SidebarChat`** — `OrgCanvasView` calls `startConversation` once `chatReady` is true (workspaces + hidden list + share preload all resolved), then keeps the conversation's `context` (canvas ref, breadcrumb, selected node id) in sync via `updateActiveContext`. `SidebarChat` is a pure renderer over the active conversation; it never owns chat state, so unmounting it (e.g. a tab switch) is cheap and idempotent. **Auto-save runs at the page level**, not inside `SidebarChat` — `useCanvasChatAutoSave` mounts in `OrgCanvasView` and survives chat unmounts, so pending writes never get dropped by tab navigation.
- **Store performance contract — read this before adding a consumer.** The streaming write path commits one `set()` per stream chunk (~50/sec). To keep that cheap:
  1. **Always select.** Never call `useCanvasChatStore()` without a selector — that subscribes to the whole store and re-renders on every text-delta. Use `useCanvasChatStore((s) => s.x)` instead. The single biggest footgun.
  2. **Use `useShallow` for derived collections.** A selector that returns a fresh array/object on every call (e.g. `Array.from(s.conversations.values())` or `messages.map(...)`) defeats Zustand's `Object.is` bail-out → re-renders constantly. Wrap with `useShallow` from `zustand/react/shallow`.
  3. **Stable empty-array sentinels.** When a selector might return `undefined` (e.g. no active conversation), fall back to a module-level `const EMPTY_X: T[] = []` instead of `?? []` — the latter creates a new `[]` every time, breaking identity equality. See `EMPTY_MESSAGES` / `EMPTY_TOOL_CALLS` in `SidebarChat.tsx`.
  4. **Select narrowly.** `SidebarChat` selects `messages`, `isLoading`, `activeToolCalls` separately rather than the whole conversation object, so the canvas's `proposals` selector is unaffected by chat streaming, and vice versa. When the canvas grows badge/halo subscribers for proposals/sub-agents/artifacts, follow the same pattern: select the specific slice you render, not "the conversation."
- **Identity-based autosave — never lose a message.** `useCanvasChatAutoSave` tracks a per-conversation `persistedIdsRef: Set<messageId>`, not a count. The save delta is `computeUnsaved` (local messages whose id isn't persisted, in order — so a creating POST always *leads with the real first user message*, never a placeholder-titled assistant row), and live-sync uses `mergeServerMessages` (keep all local rows, append server rows we don't already have, by id). Both operate on identity, so a mid-turn Pusher nudge can never drop a local message: merge only adds; the delta only sends ids not yet on the server. The merge runs only when the conversation is idle (no unsaved local messages, not streaming, no save in flight); a nudge that arrives mid-turn is deferred and retried after the next successful save. Ephemeral seeds (the AttentionList intro; the messages a joined/share conversation already has on the server) are pre-seeded into `persistedIdsRef` so they're never re-sent. The pure helpers in `canvasChatPersistence.ts` are unit-tested in `src/__tests__/unit/canvas/canvasChatPersistence.test.ts` (incl. the seed→user→planner-nudge lifecycle that used to drop the first message).
- **Conversation title self-heals.** The title is generated once at create time from the first user message (`generateTitle` in `src/lib/ai/conversationHelpers.ts`). If the creating POST's delta ever leads with a non-user row, the title freezes as `UNTITLED_CONVERSATION`; the org PUT route recomputes it from the full message list the moment a user message lands (and the history popover treats the placeholder as empty, falling back to the first-user-message preview). The identity-based autosave (above) makes the freeze rare — the creating delta now always leads with the real user message — but the heal covers legacy rows.
- **Approved feature → `<SubAgentRunCard>` requires the conversation id to round-trip.** When the user approves a feature proposal, `handleApproval.approveFeature` stamps `Feature.parentCanvasConversationId = <SharedConversation.id>` and seeds the feature's plan chat → the Stakwork planner runs → its plan posts back through the `/api/chat/response` webhook → `fanOutPlannerMessageToCanvas` appends a `source.kind === "planner"` row into THAT conversation → Pusher nudge → `useCanvasChatAutoSave` live-sync merges it → `getSubAgentRunsFromMessages` renders the card. The whole chain hinges on the stamp, which needs the **server** conversation id at approval time: (1) the client (`useSendCanvasChatMessage`) sends `conversationId: conv.serverConversationId` in the `/api/ask/quick` body, and (2) the route validates it with `resolveOrgConversationRowId` (org-scoped) — **NOT** `resolveTokenAttributionRowId`, which is workspace-keyed and silently returns null for org-canvas rows (`workspaceId: null`), leaving the feature un-fanned-out and the card permanently absent. If you add a new approval side-effect that fans out to the conversation, keep both halves wired. (Diagnose a missing card with the read-only `scripts/diagnose-subagent-card.ts`: it reports, per recent feature, whether the stamp landed, and per conversation, whether a planner row is present — disambiguating the data layer from the render layer below.)
- **`<SubAgentRunCard>` renders under SUPPRESSED planner / form-answer rows.** The card hangs under the message whose id == `run.anchorMessageId`. For an **inbound-only run** — the approval flow, where the canvas agent never makes an outbound `send_to_feature_planner` tool call, so the planner's reply is the only activity and therefore the anchor — that anchor is a `source.kind === "planner"` message, whose *bubble* `SidebarChat` suppresses (`return null`-style). So `SidebarChat` must render the bubble-suppressed planner / `user-answered-planner-form` rows' anchored card anyway (via the shared `renderSubAgentRuns` helper), or the card vanishes the instant the planner replies. **Do not** restore a plain `return null` for those rows — that's the exact bug where an approved feature's clarifying-questions card never showed. The card moving "down with the latest exchange" is intentional: an inbound reply moves the anchor, which is why it must be renderable at a suppressed-row position.
- **Planner-source rows carry feature display metadata + describe content-less replies.** Inbound-only runs have no outbound tool-call output to seed the feature name/workspace from, so the fan-out echoes `featureTitle` / `workspaceSlug` / `workspaceName` onto the planner row's `source` (the `/api/chat/response` webhook selects them from the `Feature`), and `getSubAgentRunsFromMessages` seeds the run from there — without it the card reads "Unknown feature" with no plan link. All three fields are optional (legacy rows fall back to the placeholder). Separately, planner replies often carry **no prose** — the payload is a clarifying-questions FORM or a TASKS-breakdown artifact, not message text — so `runMessageDisplayText` renders a descriptive label ("Asked a clarifying question" / "Generated a task breakdown" / "Posted the plan" / "Posted an update") instead of a bare "(empty)". Outbound content-less sends keep the literal "(empty)".
- **Adding a canvas-bound chat feature?** Use the reserved slots in `useCanvasChatStore`. Proposals → `state.proposals` map; long-running agent runs → `state.subAgentRuns`. Each is keyed by id. What a message hands the reader to look at is not a slot: it rides on the message as `message.artifacts` (see below), and the older `state.artifacts` / `message.artifactIds` registry is unused. If you find yourself emitting a Pusher event from the chat to the canvas (or vice versa), stop — that's what the store is for.
- **Synthetic intro / "top items needing your attention".** First registered artifact type is `attention-list` (`src/app/org/[githubLogin]/_components/AttentionList.tsx`). On fresh canvas entry `OrgCanvasView` fetches `/api/orgs/[githubLogin]/attention?limit=3` (backed by `src/services/attention/topItems.ts`, which fans 4 signal queries — halted/failed workflows, features awaiting user feedback, tasks with FORM artifact, ready-to-review COMPLETED — across the user's accessible workspaces in the org), then seeds `startConversation` with one synthetic assistant message + a registered artifact of `type: "attention-list"`. The seed is **ephemeral**: `startConversation` accepts `ephemeralSeedCount`, which `useCanvasChatAutoSave` reads to skip leading messages from the first POST/PUT — so the synthetic intro never lands in `chat_conversations` and never leaks into `?chat=<shareId>` shares. Skip conditions: `?chat=<shareId>` is present (forking), or `sessionStorage["hive:attention-dismissed:<login>"] === "1"` (user clicked × this session). Dismissal flows through `state.dismissedArtifactIds` (a generic per-session dismiss set) — `OrgCanvasView` subscribes once and writes the sessionStorage flag whenever an `attention-*` id lands in it. Per-card behavior (callbacks, etc.) goes through store actions, not function-valued artifact data, so the artifact registry stays serializable. (`MessageArtifacts` in `SidebarChat` does not read this registry: it renders the refs a message carries — next bullet.)
- **A message carries artifact refs; content is read through one loader; `kind` is how Hive shows one.** What Jamie hands the reader to look at — a plan, a screenshot, a pod's browser, a pull request, logs — rides on the message as an `ArtifactRef` in `message.artifacts` (`_state/canvasChatArtifacts.ts`): `id`, `kind`, `title`, an optional `label` and `summary`, and a `source` that points at where the content lives. Nothing is registered in `state.artifacts`. The content — what a viewer draws (`ArtifactContents`) — is never stored on the message: `useArtifactContent` (`_components/artifacts/useArtifactContent.ts`) reads it when a card has been on screen or the panel opens, through React Query, so a card and the panel showing the same artifact share one read. `kind` names the renderer, never the job: a plan is `markdown`, a screenshot is `image`, a pod or a web page is `url`. What it is to the reader goes in the free-text `label`, which is displayed and never switched on. The kinds: `markdown`, `html`, `image`, `video`, `audio`, `pdf`, `url`, `diff`, `pull_request`, `code`, `log`, `json`. **`_components/artifacts/registry.ts` is the one place a kind is switched on** — each entry gives the kind's `Inline` preview (on the chat card, `ArtifactCard`; a kind without one gets a card that is its name alone), its `Panel` view (on the artifact panel, `ArtifactPanel`), and what can be done with its content (`fact`, `copyText`, `address`). Adding a kind = an entry in `ArtifactContents` with its parser + a registry entry. The same `id` on a later message is a newer version of the same artifact: each message keeps its own card ("v2"), and the panel steps between versions, following the newest unless the reader stepped back.
- **Refs and content are parsed before they render; addresses are checked before they are framed or linked.** A ref comes out of stored JSON and content out of another system, so `parseArtifactRefs` (at every hydration: `toCanvasMessages`, `hydrateServerMessages`, the fork, the `?chat=` preload) and `parseArtifactContent` (inside the loader hook) keep what is whole and drop the rest — nothing is repaired. An artifact's address was written by an agent: it becomes a link only through `artifactHref` (the registry's entries hand over the address as written) and reaches the mini browser's frame only through `webAddress` — http(s) only, both. A PDF is framed only when `framablePdfAddress` passes it (Hive's own origin, or bytes the page holds), because the browser's PDF viewer cannot run in a sandboxed frame. The mini browser's sandbox confines pages from elsewhere; a page on Hive's own origin is Hive itself and is no more confined in the frame than in a tab of its own. Stored HTML goes through `HtmlArtifactFrame` like everywhere else.
- **The writer and the reader: strut jobs.** `ArtifactSource` has two shapes: `inline` (the content is on the ref — an address, or something small) and `graph` (`swarmId` + `key`: something on that swarm's strut, `key` being strut's own link to it — `/jobs/<job>/files/<path>` for a file in a job's directory, `/artifacts/<runId>/<path>` for a run's own). An `inline` ref is read straight off the ref. A `graph` ref goes through the loader (`ArtifactLoaderContext`'s default, `readStrutArtifact` in `useArtifactContent.ts`), which reads it through **one Hive route**, `GET /api/orgs/[githubLogin]/strut/artifacts?swarmId=&key=` — session auth, the swarm must be a workspace of the org the caller can read, the key must be one of the two link shapes AND name a job or run a `StrutRun` row says Hive launched there, then the bytes are streamed from the swarm with strut's `content-security-policy: sandbox` and `x-content-type-options: nosniff` kept and `cache-control: private, no-store`. Text kinds (`markdown`, `log`, `code`, `json`) are fetched and shaped by the loader; media, a PDF and a `url` are handed to their viewers as that reader URL (Hive's own origin, so the PDF frame rule passes; a page strut wrote is shown as `url` — a static page, the reader keeps its sandbox — because tom's `html` content is a stored Hive page by slug). **The writer** is the `job_turn` completion handler (`services/strut-runs/job-turn.ts`, strut `plans/jobs.md`): `start_job` / `continue_job` (`lib/ai/strutTools.ts`) launch the org strut's seeded `job` workflow with a job id Hive minted, and when a turn settles the handler reads strut's resolved artifact list (`GET …/runs/<id>/artifacts`), maps it to refs (`mapStrutArtifacts`: a strut-relative url → `graph`; an absolute url or inline content → `inline`) and appends ONE assistant row (`source: { kind: "job", jobId, … }`, header `**Job · <jobId> · <title>**`, `artifacts` on the row — `StoredMessage.artifacts`) with the fan-out discipline of `canvas-strut-fanout.ts`. `ArtifactLoaderContext` lets a test or a demo stand in for the reader. Still open on the live path: live-sync only appends rows it has not seen (`mergeServerMessages`) and skips the rows of a turn this tab sent, so the job row reaches an open tab through the `job` Pusher nudge (a new row, not one patched in place — which is why the handler appends rather than patches). `html` refs would sit beside `HtmlPageCard` (built from `save_html` tool output) as a second card for the same page — the job writer never emits `html`, so nothing collides yet.
- **A job row is the record; Jamie's wake is the reply.** A job turn's row (`source.kind: "job"`) is what the job's agent wrote, in full — a code change lists files, functions and line numbers — so `SidebarChat` renders it as `JobTurnCard`, collapsed to its title and how the turn ended (Done / Needs an answer / Failed / Stopped / Lost); a click opens the full reply, and what stays visible collapsed is the job's **Question for you** or a failed turn's one-line reason. The artifact cards render under the card as for any message. The readable reply is the canvas agent's own turn: once the row lands (exactly once, on `appended`), `handleJobTurnSettled` schedules `invokeCanvasAgentOnJobTurn` (`services/canvas-strut-autoturn.ts`, the same runner as the settled-chat wake) in `after()`, with the outcome, the question and the titles of the cards; its wake message — and the strut capability snippet — tell the agent to write ONE short paragraph in its own words, never restate the entry, never list files/functions/line numbers, never describe the cards, or to `continue_job` when the user's instructions already answer the question, or to stay silent. Same gates as every autonomous turn (the owner's `canvasAutonomousTurns` opt-in, the master kill switch) and the same loop breaker, which now counts `start_job` / `continue_job` as launches alongside `dispatch_strut`. The callback's host rides to the handler as `StrutRunHandlerContext.publicBaseUrl` (what a `continue_job` made on the wake turn builds its callback URL from); the reconcile path has no request and falls back to the deployment's own URL. Stored job rows still reach the model as text on the next human message, header line included. Before the row lands, the launch alone is the card: `getPendingJobTurnsFromMessages` (`JobTurnCard.tsx`) walks the conversation in order and pairs each `start_job` / `continue_job` call strut accepted (`status: started | continued`) with the job row that follows it — a job has one unsettled turn at a time, and the server persists the launching turn before a job turn can settle — and a launch with no row yet renders `PendingJobTurnCard` (the title, a spinning **Running** pill) under the message that made the call, beside the raw tool card the way the strut chat card sits beside `dispatch_strut`. A pure projection like that card, so it survives reload and reaches other tabs with the persisted `toolCalls`, and it cannot stick: Stop cancels the run on strut, which posts back a Stopped row; a run strut never reports is reconciled to a Lost row after `STRUT_RUN_RECONCILE_MIN_AGE_MS`. A refused launch (`busy`, `error`) or an interrupted call draws nothing.
- **The artifact panel takes the left panel; `state.artifactPanel` says what is on it.** A card calls `openArtifactPanel(id, version?)`; `OrgCanvasView` watches `useArtifactPanelOpen()` and derives what has the left panel once (`leftSurface`: the canvas, the chat list, or the artifact): the panel takes the canvas's place (the canvas unmounts, as it does for the control panel) while the chat stays where it is. On the control panel the list gives way instead and the chat steps back from stage width to the sidebar's; the control panel keeps its state and only stops fetching and taking keys while its list is covered (`useControlPanel`'s `listVisible`). Escape, the panel's ×, switching views, pulling a plan onto the stage, changing conversation (`startConversation` / `setActiveConversation` clear the slot — an artifact belongs to the chat it came from) or leaving the page all close it.
- **Chat input prefill via `pendingInputDraft`.** A canvas affordance can compose a chat message *for* the user without a DB write or agent tool call: write the text to `useCanvasChatStore.pendingInputDraft` and switch the panel to the Chat tab. `<SidebarChatInput>` watches the slot in an effect, applies the value to its local `input` state, focuses + caret-to-end, then immediately clears the slot via `setPendingInputDraft(null)` so a tab-switch back doesn't re-apply. The user can edit and send normally. The canonical use today is the Connections link-mode `+ Create connection` button (`Make a connection document between A and B`). This is the canonical pattern for "canvas affordance composes a chat message" — proposals, agent suggestions, etc. should reuse `pendingInputDraft` rather than reaching imperatively into the textarea ref.
- **Stop: the composer's Send becomes Stop while a turn runs.** From send until the reply ends, the conversation's `activeTurn` is set and every send waits for it: `useSendCanvasChatMessage` refuses, `ProposalCard` disables Approve / Reject, and a research kickoff goes to `pendingInputDraft`. `stopCanvasChatTurn` POSTs `/api/ask/abort` with the turnId; the server writes a Redis key (`services/canvas-turn-abort.ts`) that the instance generating the turn polls, aborting `streamText` — a running repo_agent tells stakgraph to stop, and sub-agents the turn dispatched but hadn't started are fanned out as `cancelled`. Only once the server accepts does the tab abort its own request and end the turn locally: unfinished tool calls become `interrupted` and a `source.kind: "stopped"` row follows. The server persists the same shape under `${turnId}-a*` (this tab keeps its own copy; the authored-turn filter skips the server's). `toModelMessages` — one function for server history and the client-sent history — gives every tool call a result and replays the stopped row as a notice from the user. Closing the tab never stops a turn; sub-agents that started after the reply ended run to completion. **Edit and send again:** a turn this tab stopped (`stoppedTurnId`) offers Edit on its message, which puts it in the composer (`editingTurnId`); sending then passes `replacesTurnId`, and the stopped turn leaves the transcript — locally (`removeTurn`; local rows carry the server's `${turnId}-…` ids, so a turn is one prefix on both sides) and on the server (`removeStoppedTurn`, only for the caller's own stopped turn per Redis, and only while it is still the last turn). A stopped turn whose reply is still being saved drops that save once replaced (`appendTurnMessages`' `requireRowId`).
- **The Control panel (`?view=control-panel` on the org page) shares this store.** It is the org page's other view: `OrgCanvasView` keeps owning the conversation lifecycle (`startConversation` once workspaces + the optional `?chat=` preload resolve, `updateActiveContext` on changes, `useCanvasChatAutoSave` + `useSubAgentStatusRefresh` at page level) and, in that view, puts the chat list in the left panel (`ControlPanelList`, state from `useControlPanel`) and turns the right panel into the stage (`OrgRightPanel` with `controlPanel` set) — the same mounted `<SidebarChat>`, so switching views never remounts the chat and a chat opened on the control panel *is* the chat the canvas shows; a plan on stage is the real plan page (`PlanChatView` with `embedded`). The plan/task on the control panel's stage rides along as `selectedNodeId` (`feature:<id>` / `task:<id>`), exactly like a canvas click, so "this" in a message means what's on stage. Every "open this stored chat" affordance — the history popover, the automations inbox, control panel rows — goes through `openOrgConversation` (`_state/openOrgConversation.ts`); `startNewOrgConversation` is the shared "fresh chat in its own slot + drop `?chat=`" path. Don't add a fourth copy.
- **What's NOT in this store.** Voice transcript / mic state lives in `src/stores/useVoiceStore.ts` (separate concern, separate lifetime — mic-session-scoped, available across surfaces). When voice transcription wants to drop a finalized transcript into the canvas chat, it calls `useCanvasChatStore.getState().appendUserMessage(...)`. **The dashboard chat does NOT use this store.** `DashboardChat` keeps its own local state on purpose; the two surfaces are diverging. Don't try to unify them — when a feature lives on both, share the lower-level pieces (`useStreamProcessor`, message types), not the state layer.
